# Interview Prep — Churn Prediction Service

## 2-minute explanation

"I built a churn prediction service the way I would build a small
production system. It generates 5,000 synthetic telecom customers
with a fixed seed, splits them 60/20/20, and trains two candidates:
histogram gradient boosting and a logistic-regression baseline, each
inside a pipeline with shared preprocessing. Model selection happens
on validation ROC-AUC, then the winner gets isotonic calibration via
cross-fitting on the training set, and test is touched exactly once
for final metrics. Everything is logged locally in MLflow style, one
JSON record per run, with no server. The model is served by a FastAPI
app with health, model-info, and predict endpoints, and there is a
Dockerfile that trains at container start and then serves. On this
synthetic data the logistic baseline actually won validation, 0.745
to 0.698, which makes sense because the labels were generated by a
logistic function, and calibration did not improve test calibration,
which I report rather than hide. The service fails fast if the model
artifact is missing, and unknown categories at predict time are
handled instead of crashing."

## Architecture walkthrough

- `src/data_gen.py`: fixed-seed generator. Features are drawn from
  plausible distributions (gamma tenure, charges conditional on
  internet service, Poisson support calls), and the label comes from
  a logistic function of the features plus noise. Customer IDs carry
  a `SYN-` prefix.
- `src/features.py`: one `ColumnTransformer` used by both candidates
  and by serving: median imputation + `StandardScaler` for numerics,
  most-frequent imputation + one-hot with `handle_unknown="ignore"`
  for categoricals. Fitting happens inside the Pipeline, so
  preprocessing statistics come from training folds only.
- `src/model.py`: candidate builders, isotonic calibration wrapper,
  metric functions (ROC-AUC, average precision, Brier, ECE,
  calibration table), and `log_run` for local JSON run records.
- `train.py`: the orchestration CLI. Split, train, select, calibrate,
  evaluate once on test, save the joblib artifact, write
  `results/metrics.json`, append a run log.
- `api.py`: FastAPI app. Loads the artifact at import and fails fast
  if it is absent. Pydantic schema validates the request; the
  response is a probability, a 0.5-threshold prediction, and the
  threshold itself.
- `Dockerfile`: slim Python image, installs requirements, trains at
  container start, then serves with uvicorn. Not build-verified here
  (no Docker in this environment); the README says so.
- `tests/test_churn.py`: 12 tests — generator determinism and label
  range, unseen-category and NaN handling in preprocessing,
  candidates beating chance, calibration-table accounting, run-log
  writing, and API behavior via `TestClient` (health, predict shape,
  422 on bad input).

## Design tradeoffs

- **Two candidates, validation-selected.** A baseline exists so the
  strong model has to earn its place. On this data it did not, and
  the pipeline correctly picked the simpler model.
- **Cross-fitted calibration on train.** Calibrating on validation
  would have been simpler, but sklearn 1.9 removed `cv="prefit"`,
  and cross-fitting on train keeps calibration fully separate from
  both selection and final evaluation.
- **Local JSON run logs instead of MLflow.** No server to run, no
  network dependency, and the record format is transparent. The cost
  is no UI and no experiment comparison tooling; for a portfolio
  project that tradeoff is right.
- **Fail fast in the API.** If the artifact is missing, the service
  refuses to start. Serving a dummy or stale model silently would be
  worse than an explicit error.
- **Fixed 0.5 threshold, reported.** Threshold tuning is a business
  decision (cost of false positives vs false negatives); the service
  returns the probability so callers can apply their own threshold,
  and the 0.5 default is stated, not hidden.

## Limitations (say these before being asked)

- Synthetic data generated by a logistic process flatters logistic
  regression and makes calibration look unnecessary. Real data would
  likely change both conclusions.
- No tuning, no threshold optimization, no drift monitoring, no auth
  or rate limiting on the API.
- The Dockerfile is written but unverified here.
- Single artifact, no versioning or rollback story beyond run logs.

## Future improvements

- Cross-validated hyperparameter search with per-run logging.
- Threshold tuning on validation for a stated business metric.
- Input drift monitoring against the training reference.
- Versioned artifacts with champion/challenger evaluation.
- CI running the test suite, and a verified Docker build.

## Likely interview Q&A

**Q: Why did logistic regression beat gradient boosting?**
A: Because the synthetic labels were generated by a logistic
function of the features, so the true decision boundary is linear in
the logit. Gradient boosting can fit it too, but with 3,000 training
rows and default-ish settings it overfits noise instead. The honest
takeaway is that the pipeline's job is to let validation decide
rather than assume the complex model wins.

**Q: Calibration made ECE slightly worse. Why keep it?**
A: Because the pipeline should measure calibration rather than
assume it. On this data the uncalibrated model was already close to
calibrated, so isotonic calibration had nothing to fix and added a
little noise. On real data, especially with a tree model, calibration
often helps a lot. Keeping the step and reporting both numbers is
more trustworthy than dropping it because it didn't help once.

**Q: How do you prevent leakage?**
A: Three things: the split happens before any fitting; preprocessing
is fitted inside the Pipeline on training data only; and test is
used exactly once, after selection and calibration are frozen.
Calibration uses cross-fitting on train, so no calibration fold ever
sees its own training rows' labels twice.

**Q: What happens when the API gets a category it never saw?**
A: The one-hot encoder ignores unknown categories, so the row is
encoded with zeros for that feature group and prediction proceeds.
That is tested explicitly. The alternative, erroring, would make the
service brittle to new payment methods or plan names.

**Q: Why local run logs instead of real MLflow?**
A: For a self-contained portfolio project, a server dependency is a
liability: the demo should run with one command. The JSON records
carry the same essentials MLflow would: parameters, metrics, and
data provenance. In a team setting I would use MLflow or Weights and
Biases for the comparison UI and artifact store.

**Q: How would you monitor this in production?**
A: Log prediction distributions and feature distributions, compare
them to the training reference with a drift statistic, track
calibration on labeled outcomes as they arrive, and alert when
either drifts past a threshold. Retraining would be triggered by
those signals, not by a calendar.
