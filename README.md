# Churn Prediction Service

A production-style churn prediction service: synthetic telecom-style
customer data, a scikit-learn training pipeline with model selection
and calibration, local MLflow-style run logging, a FastAPI prediction
service, and a Dockerfile. Everything runs locally with no external
services and no network calls.

## Data disclosure — read this first

**All data in this project is synthetic.** Customers are invented by
`src/data_gen.py` with a fixed seed (seed 42, 5,000 customers). There
are no real customers, no real billing records, and no real churn
outcomes. The churn label is drawn from a logistic function of the
features, so the data has learnable signal with realistic noise, but
it is not a real customer base and the model must not be presented
as trained on real data. Customer IDs are prefixed `SYN-`, and every
metrics file and run log is labeled `synthetic_data: true`.

## What it does

`train.py` runs the full pipeline:

1. Generate 5,000 synthetic customers (12 features + churn label).
2. Stratified 60/20/20 train/validation/test split (seed 42).
3. Train two candidates on train: histogram gradient boosting
   (`HistGradientBoostingClassifier`) and a logistic-regression
   baseline, each inside a Pipeline with the shared preprocessor
   (median imputation + scaling for numerics, most-frequent
   imputation + one-hot encoding with unknown-category handling for
   categoricals). Select by ROC-AUC on validation.
4. Calibrate the winner with isotonic calibration via 3-fold
   cross-fitting on the training set. Calibration never touches
   validation or test data.
5. Evaluate once on test: ROC-AUC, average precision, Brier score,
   expected calibration error (10-bin), and a full calibration table.
6. Save the model artifact (`models/churn_model.joblib`, generated,
   git-ignored), the metrics JSON (`results/metrics.json`), and a
   local run log (`runs/run_NNN.json`, MLflow-style: parameters,
   metrics, data provenance, no server).

`api.py` serves the model over FastAPI: `GET /health`,
`GET /model_info`, `POST /predict`. The service fails fast at startup
if the model artifact is missing, rather than serving dummy
predictions. Unknown categorical values at predict time are handled
by the one-hot encoder's `handle_unknown="ignore"`.

## Measured results

Measured by running `./demo.sh` (5,000 synthetic customers, seed 42;
3,000 train / 1,000 validation / 1,000 test; overall churn rate
0.406). Two consecutive runs produced identical metrics.

| metric | value | context |
|---|---|---|
| Validation ROC-AUC, HistGB | 0.6978 | 1,000 synthetic validation rows |
| Validation ROC-AUC, LogReg | 0.7447 | 1,000 synthetic validation rows |
| Selected model | LogReg | higher validation ROC-AUC |
| Test ROC-AUC (calibrated) | 0.7534 | 1,000 synthetic test rows |
| Test average precision | 0.6629 | same test set; positive rate 0.406 |
| Test Brier, uncalibrated | 0.1966 | same test set |
| Test Brier, calibrated | 0.1966 | same test set |
| Test ECE (10-bin), uncalibrated | 0.0254 | same test set |
| Test ECE (10-bin), calibrated | 0.0327 | same test set |

Two honest observations:

- The logistic-regression baseline beat gradient boosting on
  validation. That is expected here: the synthetic labels were
  generated by a logistic function, so a linear model matches the
  true decision surface. The pipeline selects by validation score
  rather than assuming the fancier model wins.
- Isotonic calibration did **not** improve test calibration on this
  data: Brier was unchanged (0.1966) and ECE slightly worsened
  (0.0254 to 0.0327). The uncalibrated logistic model was already
  close to calibrated, which is again consistent with logistic
  synthetic data. Calibration is kept in the pipeline and measured
  rather than assumed helpful; on real data the result could
  easily go the other way.

These numbers describe this synthetic dataset only. They are not
claims about churn prediction in general.

## How to run

```bash
./demo.sh            # creates .venv, trains, tests, smoke-tests the API
```

Or manually:

```bash
python3 -m venv --system-site-packages .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python train.py [--n 5000] [--seed 42]
.venv/bin/python -m unittest discover -s tests
.venv/bin/uvicorn api:app --port 8000
curl -X POST localhost:8000/predict -H "Content-Type: application/json" \
  -d @examples/predict_request.json
```

Docker (trains at container start, then serves on port 8000):

```bash
docker build -t churn-service .
docker run -p 8000:8000 churn-service
```

Note: the Dockerfile was written but **not** verified by a build in
this environment, because Docker is not installed here. The local
`./demo.sh` path is the verified one.

## Project layout

```
src/data_gen.py       synthetic customer generator (fixed seed)
src/features.py       shared preprocessor (ColumnTransformer)
src/model.py          candidates, calibration, metrics, run logging
train.py              CLI: generate, split, train, select, calibrate, evaluate
api.py                FastAPI service (/health, /model_info, /predict)
examples/             sample prediction request (synthetic customer)
tests/test_churn.py   12 unit tests (stdlib unittest + FastAPI TestClient)
Dockerfile            trains at start, then serves (build unverified here)
results/metrics.json  metrics from the verified run (small, committed)
models/               generated model artifact (git-ignored, regenerable)
runs/                 local run logs (git-ignored)
```

## Limitations (honest)

- The data is synthetic and generated by a logistic function, which
  flatters logistic regression and makes calibration look
  unnecessary. Real churn data would behave differently.
- No hyperparameter tuning, no feature selection, no class-imbalance
  handling beyond what the data happens to contain.
- The API is a single-process demo service: no authentication, no
  rate limiting, no request logging, no model versioning beyond the
  run logs.
- No drift monitoring or retraining loop; the model is a fixed
  artifact until `train.py` runs again.
- The Dockerfile is unverified in this environment (no Docker here).
- No XGBoost: the gradient-boosting candidate is scikit-learn's
  histogram implementation. The README does not claim otherwise.

## Future improvements

- Hyperparameter search with cross-validation, logged per run.
- Probability-threshold tuning on validation for a business metric
  (e.g. precision at a fixed recall), instead of the fixed 0.5.
- A drift check comparing incoming feature distributions to the
  training reference, with an alert threshold.
- Model registry semantics: versioned artifacts, champion/challenger
  comparison, rollback.
- Verify the Docker build in an environment with Docker, and add a
  CI workflow that runs tests on push.
